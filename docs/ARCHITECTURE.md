# Architecture

Zagros is a Cargo workspace that produces **one binary** (`web`). The same process serves HTTP, runs the live-chat hub, applies the
database migrations at start-up and — when enabled — runs the Telegram bot as a background task. There is no separate worker or queue.

```
                     ┌──────────────────────────── one process: `web` ────────────────────────────┐
 browser  ──HTTP──▶  │  Axum router ─▶ handlers ─▶ askama templates (+ HTMX partials) ─▶ HTML      │
 (HTMX, Alpine,      │      │  layers: compression · asset caching · CSRF guard · body limits      │
  WebSocket chat)    │      ▼                                                                      │
                     │  db crate (sqlx) ◀──────────────────────────────▶ PostgreSQL 16             │
                     │      ▲                                                                      │
 Telegram ◀─poll───▶ │  bot crate (reqwest)        payments crate ◀─▶ Zarinpal / Zibal             │
 SMS / SMTP ◀────────│  sms crate ─▶ Kavenegar / SMS.ir / console   mailer (lettre) ─▶ SMTP        │
                     └─────────────────────────────────────────────────────────────────────────────┘
```

## Crates

| Crate | Responsibility | Depends on |
|---|---|---|
| `domain` | money (rial at the payment gateway, toman in the UI), shared error types — no I/O | — |
| `db` | every SQL query, row models, the embedded migrations runner (`sqlx::migrate!("../../migrations")`) | `domain` |
| `payments` | the `PaymentGateway` trait (`request` → redirect → `verify`) and its Zarinpal and Zibal implementations | — |
| `sms` | the `SmsSender` trait with Kavenegar, SMS.ir and a console implementation for development | — |
| `bot` | Telegram bot: long polling over `reqwest`, `/start <code>` account linking, `/points`, `/help` | `db` |
| `web` | the application: configuration, routes, templates, authentication, CSRF guard, uploads, mailer, chat hub, SEO | all of the above |

Gateways and SMS providers are chosen from configuration at start-up (`payments::build`, `sms::build`); adding a provider means one
new module that implements the trait.

## Request flow

1. **Router** (`crates/web/src/routes/mod.rs`) groups public pages (home, catalogue, product, cart, checkout, offers, static pages,
   `sitemap.xml`, `robots.txt`, `/health`), the customer account (`/account/…`), support (tickets, WebSocket chat), repairs, returns and
   the `/admin/…` panel.
2. **Layers** in the app: Brotli/gzip compression, long-lived `Cache-Control` for static assets, an 8 MB body limit on uploads, and
   the **CSRF guard** (`csrf.rs`) — a token-free same-origin check of `Origin`/`Referer` on `POST/PUT/PATCH/DELETE`, backed by
   `SameSite=Lax` cookies. TLS, HSTS, `nosniff`, rate limiting and the WebSocket upgrade are handled by nginx (`deploy/nginx.conf`).
3. **Extractors** (`extract.rs`) resolve the signed session cookie to a user; admin routes require `role == "admin"`.
4. **Handlers** call the `db` crate, build an askama template and return HTML. HTMX requests receive small partials
   (`routes/partials.rs`: header, menu, mini-cart and its badge, footer, search suggestions) so those widgets update without a page load.
5. **Site settings** (name, contact, shipping cost, payment toggle, points rate …) live in the `settings` table and are read at
   request time, so admin changes apply without a restart. A few read-mostly pages use a small in-memory TTL cache (`TtlCache`).

## Authentication and sessions

- Login is by **mobile number and a one-time code**. The code is generated by the app, stored hashed (argon2id) in `otp_codes`,
  expires, and is delivered through the configured SMS provider (or printed to the log in console mode).
- The session id lives in a **signed cookie** (`axum-extra` `SignedCookieJar`, key derived from `ZAGROS__SERVER__COOKIE_SECRET`);
  active sessions are listed in `user_sessions` and can be revoked from the account page.
- The first administrator is bootstrapped with `ZAGROS__ADMIN__MOBILE`: that number is promoted to `admin` at every start.

## Checkout and payment

`checkout` builds the order from the cart in **one transaction** (stock is decremented atomically, coupon caps are locked against
concurrent use). Cash on delivery confirms immediately. Online payment calls `PaymentGateway::request`, redirects to the gateway and
returns to `/payment/callback`, where `verify` is called with the **amount re-checked**. A failed payment restores the stock; a
cancelled order restores stock and any spent points. After a confirmed order the loyalty hook awards points **idempotently** and
notifies the linked Telegram chat; errors there are logged and never break the order flow.

## Live chat

Each chat session has an in-memory `tokio::sync::broadcast` channel (`ChatHub`) that fans messages out to the customer and operator
WebSockets; every message is also written to `chat_messages`, so history survives restarts. Because the hub is in memory, run a
single instance of the app behind the proxy.

## Data model

Migrations are append-only SQL files in `migrations/` (`0001` schema … `0019` sessions; `0003` holds the seed data). Main groups:

| Area | Tables |
|---|---|
| Catalogue | `categories`, `brands`, `products`, `product_variants`, `product_images`, `attributes`, `product_attributes` |
| Commerce | `carts`, `cart_items`, `orders`, `order_items`, `payments`, `addresses`, `settings` |
| Accounts | `users`, `otp_codes`, `user_sessions`, `wishlists`, `notifications` |
| Engagement | `product_reviews`, `review_helpful`, `product_questions`, `product_answers`, `stock_alerts`, `banners` |
| Loyalty and money | `loyalty_transactions`, `coupons`, `coupon_redemptions`, `gift_cards`, `wallet_transactions`, `telegram_link_codes` |
| After-sales | `repair_requests`, `repair_status_log`, `tickets`, `ticket_messages`, `chat_sessions`, `chat_messages`, `returns`, `return_items`, `return_status_log` |

Search uses `pg_trgm` and `unaccent` (Persian-aware matching); ids are UUIDs (`uuid-ossp`).

## Design decisions

- **Self-hosted everything** — fonts, HTMX, Alpine and CSS are served from `assets/`; there is no CDN or third-party script, so the site
  keeps working when the international internet is unreliable.
- **Server-side rendering first** — good SEO, fast first paint on weak devices, and very little JavaScript.
- **Small footprint** — one process, in-process chat hub and bot, thin caching; the unit file caps memory and `.cargo/config.toml`
  keeps builds to one job for tiny build machines.
- **Rial at the boundary, toman in the UI** — all gateway amounts are integers in rial; presentation converts.
